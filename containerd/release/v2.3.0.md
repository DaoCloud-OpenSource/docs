# containerd 2.3.0 作为 LTS 版本正式发布

[containerd v2.3.0 release](https://github.com/containerd/containerd/releases/tag/v2.3.0)

`containerd v2.3.0` 已正式发布。这是 containerd 2.x 的第三个 minor 版本，也是项目进入新发布节奏后的第一个年度 LTS 版本。`2.3` 已成为正式 LTS；minor 发布节奏开始与 Kubernetes 对齐，约每 4 个月发布一次。

从生产环境角度看，2.3.0 的重点集中在几个方向：shim 启动协议、链路可观测性、EROFS 镜像与挂载路径、CRI 能力补齐、NRI 插件生态，以及容器文件系统传输接口。

## Containerd 2.3 作为 LTS 正式落地

在 `RELEASES.md` 中，containerd `2.3` 已标记为 `LTS`，生命周期为 `2026-04-30 (UTC)` 到 `2028-04-30`；`2.4` 进入 `Future` 状态，计划窗口为 `2026-08-26` 到 `2027-04-26`（`tentative`）。

containerd 升级策略明确支持相邻 minor 升级，也支持相邻 LTS 的直接升级。例如从 `1.7 LTS` 到 `2.3 LTS` 的路径会被测试和支持。

状态上需要注意两个时间点：

- `1.7` 作为 1.x LTS，计划在 `2026-09` 结束扩展支持。
- `2.1` 的 EoL 日期是 `2026-05-05`，按当前日期（`2026-05-07`）已经过期。

## Shim 启动协议重构

2.3.0 引入了新的 `shim bootstrap protocol`。

过去 containerd 启动 shim 时，参数来源较分散，包括 CLI 参数、环境变量、stdin、spec 文件等。随着 runtime 和 sandbox 能力扩展，这种方式会增加兼容成本，也容易产生隐式行为。

新的 bootstrap protocol 使用 `BootstrapParams` 和 `BootstrapResult` 描述启动输入与输出，让 containerd 与 shim 之间的契约更明确，也更便于后续版本演进。

这项变化对自定义 runtime、外部 shim、sandboxer 相关实现影响较大。2.3 仍保留旧启动路径的兼容 fallback，不是一次性切断旧实现，但建议提前验证自研 runtime 是否依赖旧参数路径。

## 日志与 Trace 打通

2.3.0 加强了 OpenTelemetry 相关能力。

一方面，containerd 支持将 Trace ID 注入日志字段。开启 `log_trace_id` 后，日志中可以带上对应 trace ID，便于从日志直接跳转到链路追踪系统。

另一方面，插件客户端的出站 RPC 开始传播 trace 上下文。此前 tracing 更多停留在服务端入口，现在跨插件调用链路也能串起来。

这对线上排障很实用。containerd 问题经常跨越 CRI、snapshotter、runtime、shim、NRI 或外部插件。日志和 trace 对齐后，定位“请求卡在哪个组件”“哪个插件调用耗时异常”会更直接。

## EROFS 镜像与挂载路径增强

EROFS 是 2.3.0 中变化较多的一条线。

2.3 新增了 EROFS layer media type：

```text
application/vnd.erofs.layer.v1
```

同时支持 zstd-wrapped EROFS layer：

```text
application/vnd.erofs.layer.v1+zstd
```

这意味着 EROFS 镜像可以在分发阶段使用 zstd 压缩，在运行时保持文件系统挂载路径优势。

挂载路径也有增强。2.3 引入 `fsopen`、`fsconfig`、`fsmount`、`move_mount` 等新 mount API 路径，用来规避传统 `mount()` 在复杂 mount options 场景下可能遇到的 `PAGE_SIZE` 限制。

此外，erofs snapshotter 增加了 dm-verity 支持。对于镜像完整性要求较高的场景，dm-verity 可以提供更明确的只读校验能力。不过这也依赖节点内核与相关模块支持，生产启用前需要单独验证。

对 EROFS 的评估不应只看拉取速度。更合理的验证维度包括镜像构建、registry 分发、节点内核支持、snapshotter 配置、启动时延、异常回滚和完整性校验。

## CRI 能力补齐

2.3.0 在 CRI 侧补了几项关键能力。

首先，容器现在可以同时使用 `hostNetwork` 和 `user namespace`。这个组合过去在部分场景下受限，2.3 之后网络兼容性和用户命名空间隔离可以同时存在。

其次，`UpdatePodSandboxResources` 已接入 Sandbox API。这样 CRI 资源更新可以路由到 sandbox controller，同时在旧 sandboxer 不支持时保留兼容处理。

CRI stats 也有增强。2.3 增加后台统计收集器，用于计算 `UsageNanoCores`。这对依赖 CRI stats 的 kubelet 路径和监控系统有实际影响。

另外，CRI `ContainerStatus` 与 `ListContainers` 响应会填充 `ImageId`。在多架构镜像场景下，这个字段有助于识别节点实际运行的 image config digest，而不是只看到 manifest list digest。

## NRI 插件生态继续扩展

2.3.0 对 NRI 做了较多增强。

NRI 插件现在可以获得更多上下文信息，包括 container user、seccomp policy、POSIX rlimits、扩展容器状态、CDI devices、Linux sysctl 等。

NRI wire protocol 增加了更明确的 pod/container 生命周期 RPC。插件注册时会交换 NRI 版本，NRI framework 也补充了基础指标。

资源调整能力同样扩大，包括 memory policy、Intel RDT、调度策略、网络设备和 sysctl 等。

这些变化让 NRI 更适合承载资源隔离、设备注入、QoS、调度策略和合规审计类插件。

升级时要特别检查一个 breaking change：NRI plugin 名称中不再允许逗号。这与 OCI hook ownership tracking 的 owner 语义调整有关。已部署 NRI 插件的环境，需要提前检查插件命名与 hook ownership 行为。

## 容器文件系统 copy transfer types

2.3.0 新增了 container filesystem copy 的 transfer types。

这个能力为类似 `docker cp` 的文件进出容器场景提供了更标准的接口基础。即使 runtime 不适合直接暴露或访问容器挂载点，也可以通过 transfer 框架表达文件复制操作。

这里需要注意边界：2.3 主要引入的是类型和 API 基础，不等于所有客户端都已经具备完整的 `docker cp` 等价能力。它更像是为后续客户端和插件生态打基础。

## 其他更新

除上述变化外，2.3.0 还有几项生产评估时建议一起检查：

- 配置迁移：plugin config migration 现在会在配置加载时执行，减少全局配置迁移与插件配置迁移分离导致的不一致。
- Sandbox API：增加 spec 字段，并继续减少对 pause container 的直接假设。
- CRI 指标：后台 stats collector 用于增强 `UsageNanoCores` 计算，并补充部分 cgroup v2 下的 CPU、memory、IO PSI 数据。
- ImageId 填充：CRI 状态响应中的 `ImageId` 更准确，有助于多架构镜像审计和运行时状态分析。
- `shim.Command` 弃用：如果自定义 shim 或 runtime 代码依赖这个接口，需要提前检查。
- 依赖升级：2.3.0 同步升级了多项关键依赖，包括 containerd API、NRI、OCI runtime-spec、OpenTelemetry 等。

## 生产升级建议

2.3.0 已经进入 GA 和 LTS 状态，但生产环境仍建议按灰度节奏推进。

1. 升级前先检查 runtime、shim 和 sandboxer。重点确认是否有自定义 runtime、外部 shim，或依赖旧 shim 启动参数路径的实现。
2. 验证日志与 trace 联动效果。建议在测试环境开启 `log_trace_id`，确认日志字段能否正确映射到现有 tracing 平台。
3. EROFS 需要单独做 A/B 测试。测试内容不只包括拉取速度，还应覆盖镜像构建、分发、挂载、启动、dm-verity、内核模块和异常恢复。
4. CRI 侧重点回归 `hostNetwork + user namespace`、`UpdatePodSandboxResources`、`UsageNanoCores`、`ImageId` 和 pod/container stats。
5. 已部署 NRI 插件的环境，需要检查插件命名、生命周期事件、版本协商、hook ownership、CDI devices、seccomp、rlimits 与 sysctl 逻辑。
6. 升级路径要提前规划。对于 LTS 用户，`2.3` 是后续从 `1.7 LTS` 迁移的重要目标版本。建议先验证 `2.3.0`，再跟进后续 `2.3.x` patch，避免一次性跨过过多补丁版本。

## 结语

containerd 2.3.0 是一个偏基础设施加固的版本。它把运行时启动协议、可观测性、镜像挂载路径、CRI 能力、NRI 插件生态和文件传输接口都向前推进了一步。

对生产团队来说，2.3 LTS 的发布意味着新一轮运行时基线已经明确。越早完成 runtime/shim、EROFS、CRI stats、NRI 和 trace-log 联动验证，后续迁移到 2.3.x 的成本越低。
